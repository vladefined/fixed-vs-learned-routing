## Методика (финальная постановка, этап 2)

### Язык v4 (`dd/grammar3.py`, `dd/data.py --version 4`)
Синтаксис + «история перестановок». Словарь 446 токенов.

```
<bos> N_1 , … , N_k said : CLAUSE ; [ORD_a and ORD_b swap ;]×m  MARK ORD_q NAME_? V .
CLAUSE -> NP ADV? VP        NP -> DET ADJ{0,2} N MOD? | NAME        MOD -> PP | RC
RC     -> who|which VP | whom NP V_tr            (без скобок; объектные RC вкладываются → центральное вложение)
VP     -> V_intr PP? | V_tr NP | V_cc  <k that CLAUSE >k      (4 случайных типа скобок)
```
* Вложенность до 8; согласование глагола с вершиной подлежащего через PP/RC с аттракторами.
* **Слежение за состоянием:** k ∈ {3, 4} имён, m ∈ {0…6} перестановок позиций, вопрос «кто на позиции q».
  Ответ однозначен ⇒ энтропия в этой точке 0, любая ошибка модели целиком идёт в CE − H.
  Для каждого предложения хранятся m, k, индекс события на каждом токене события, позиция, на которой
  модель должна выдать ответ (токен ORD_q), и сам токен ответа; для каждого токена — часть предложения
  (вступление / клауза / история). Анализ связи со структурой ведётся только по токенам клаузы.
* Грамматика однозначна ⇒ log p(предложения) известен точно; отбраковка предложений длиннее 127
  токенов (0.05%) учтена в нормировке. Train 3 млн предложений (145 млн токенов), val/test по 20 тыс.,
  пересечений нет. Строки по 128 токенов, внимание только внутри своего предложения.

Почему не v2/v3: даже модель с 0.13M параметров и 2 слоями выходила на +0.003 нат над энтропией и 100%
на всех проверках за ~70 с обучения — каждая зависимость решается одним «поиском» внимания по явной
подсказке. Слежение за перестановками требует последовательной композиции и действительно трудно для
трансформера фиксированной глубины.

### Модель (`dd/model.py`)
d = 128, 4 блока, 8 голов (по 16), SwiGLU 344, RoPE, связанные эмбеддинги. A: 0.85M параметров;
B/C/B_dd/B′: ~1.0M (W_depth 344×128 и depth_emb в каждом блоке); E/G/F: ~0.87M.

Нормированное состояние (основная схема после находки этапа 1):
```
x0 = normalize(emb)                                   normalize: RMS = 1 на токен (E, G — на группу из 16)
a = attn(rmsnorm(x) + depth_emb_a(depth));  y = x + a (временное);  h = SwiGLU_hidden(rmsnorm(y) + depth_emb_f(depth))
u = W2 h;  dd = ((l+1) − depth) · σ(W_depth h + b);  depth += dd   (полностью, без ограничения)
B, E, F, G:  x = normalize(x + min(dd,1) · tanh(a + u))
C:           x = normalize(x + min(dd,1) · tanh(u))
B_dd:        x = normalize(x + dd · tanh(a + u))                     (масштаб dd без min — для сравнения)
B′ (pull):   x = normalize(x + min(dd,1) · (tanh(a + u) − x))
A_norm:      x = normalize(x + tanh(a + u))                          (та же нормировка, без гейта и глубины)
A:           обычная pre-norm остаточная связь
G:           + в оценках внимания slope_h·(depth_q − depth_k) по глубине группы головы h
```
Детали реализации:
* normalize делит на max(RMS, 0.1): для обычных состояний это точная нормировка (dd = 0 ⇒ состояние не
  меняется — юнит-тест), а усиление при почти полном гашении состояния ограничено ×10. На практике
  минимальный RMS перед нормировкой ≈ 0.8, пол не срабатывает.
* **Протекающий гейт** (по умолчанию, c = 6): в прямом проходе точный σ(z) (точные нули возможны);
  собственные параметры гейта (W_depth, b) получают градиент, вычисленный в max(z, −c), остальная сеть —
  истинный σ′(z). Первая версия, где суррогатный градиент шёл и в сеть, расходилась на ~4000 шаге
  (W_depth рос без ограничения, фиктивный градиент через него взрывался до 10¹⁵); с истинным
  градиентом и с исправленной версией обучение стабильно.

Юнит-тесты (`tests/test_depth.py`, 58 шт.): глубина ≤ l+1 и не убывает; dd = 0 ⇒ состояние не
меняется; каузальность (выходы, глубина, autograd); изоляция предложений; RMS = 1 на токен/группу;
min(dd,1) ограничивает изменение, а глубина растёт на полный dd; B′ при полном гейте = normalize(tanh(a+u));
смещение внимания G совпадает с явной формулой; cost = средняя итоговая глубина.

### Обучение
Одинаково для всех: 40 000 шагов × 64 строки × 128 токенов, AdamW (0.9/0.95, wd 0.1 на матрицы),
lr 2·10⁻³, прогрев 500, косинус до 10%, bf16, torch.compile. A — ~4 мин, варианты с бюджетом — ~6 мин.

### Метрики (`dd/evaluate.py`)
* CE − H на val/test; NLL и точность ответа (top-1) по m = 0…6 и по k; согласование (правильная форма
  глагола против формы другого числа), в т.ч. с аттракторами; закрытие скобок (top-1).
* Потраченная глубина в зависимости от m: итоговая глубина (= Σ dd), Σ min(dd,1) и Σ по слоям
  RMS(Δx)/RMS(x) — на позиции ответа и на токенах событий.
* «Замёрзшие» координаты двумя способами: dd < 0.01 и |Δx|/RMS(x) < 0.01 (RMS по токену, для E/G — по
  группе); их расхождение (доля «dd < 0.01, но |Δx| ≥ 1%»). Разложение дисперсии маски «замёрзла» на
  статическую часть (одни и те же координаты для всех токенов), лексическую (зависит от слова) и
  контекстную. Гистограммы σ(гейта), dd и min(dd,1) по слоям.
* Проверка, что малые dd действительно не нужны: обнулить все dd < 0.01 / 0.05 / 0.1 и измерить рост CE.
* Структура (токены клаузы): частная ранговая корреляция итоговой глубины с глубиной в дереве и глубиной
  вложения при контроле класса слова и позиции (95% бутстрап по предложениям), то же внутри предложения;
  регрессия с кластеризованными ошибками на число открывающихся/закрывающихся составляющих и «главное слово».
* Поток: вред от удаления блока; эксцесс активаций по токену/по координате с контролем случайного
  поворота; Хойер. Зонд «какой это токен» по группам из 16 координат (для B — бины координат по
  средней глубине).
